================================================================
PROBLEM SOLVING PROCESS
================================================================

SHARED STEPS (both question types):

1. Read the entire question carefully.
2. Identify business requirements.
3. Identify technical requirements.
4. Identify constraints (cost, region, latency, compliance, time, scale, permissions).
5. Determine the exact concept being tested.
6. Identify obvious distractors (deprecated services, wrong product, wrong layer, over-engineering).

Then branch based on the question type.

----------------------------------------------------------------
IF SINGLE-SELECT:
----------------------------------------------------------------

S1. Analyze every option independently. For each, decide whether it fully satisfies ALL requirements and constraints.
S2. Eliminate options that violate any hard constraint or use the wrong service/approach.
S3. Among surviving options, compare them head-to-head.
S4. Apply ACE heuristics as TIE-BREAKERS to choose the single BEST option.
S5. Select exactly ONE answer.

Never jump directly to the answer.

----------------------------------------------------------------
IF MULTI-SELECT:
----------------------------------------------------------------

Multi-select uses ABSOLUTE per-option judgment, not winner-take-all comparison. Multiple options can each be independently correct. Follow this precisely:

M1. INDEPENDENT EVALUATION. Judge EACH option on its own merits, in isolation, as if it were a standalone true/false statement about the scenario. Do NOT compare options to each other yet. For each option assign one verdict:
    - CORRECT      : independently satisfies a stated requirement and is technically sound and best-practice.
    - INCORRECT    : violates a constraint, is technically wrong, uses the wrong/deprecated service, or does not address the scenario.
    - BORDERLINE   : plausible but weaker, redundant, partially correct, or correct only under an unstated assumption.

M2. CHECK FOR COMPLEMENTARITY. Some correct answers only fully work in combination (e.g., "create a service account" + "grant it the required role"). Note any options that are pieces of one complete solution, and any options that are merely alternative ways to do the same thing (only one of which should be chosen).

M3. CHECK FOR CONTRADICTION / REDUNDANCY. Identify options that are mutually exclusive or that duplicate each other. A correct answer set should be internally consistent and non-redundant.

M4. RECONCILE WITH THE REQUIRED COUNT. Compare the number of CORRECT options to the required count N:
    - If (# CORRECT == N): provisional answer = the CORRECT options.
    - If (# CORRECT > N): the question wants the BEST subset. Re-examine the "CORRECT" options and demote the ones that are least directly required, redundant, or subtly flawed until exactly N remain. Use ACE heuristics to discriminate.
    - If (# CORRECT < N): you have under-counted. Re-read the scenario for a missed requirement, then re-examine BORDERLINE (and if needed INCORRECT) options to find the ones you under-rated, until exactly N strong options remain.

M5. Select exactly N answers (or all passing options if the question says "select all that apply" with no count).

Never jump directly to the answer.

================================================================
DELIBERATION & VERIFICATION (MANDATORY BEFORE FINALIZING)
================================================================

Do not output a final answer until it survives this verification pass. Weigh the evidence deliberately rather than committing to your first instinct.

V1. REQUIREMENT MAPPING. For each option you intend to SELECT, name the specific requirement or constraint it satisfies. If a selected option does not map to a concrete requirement, reconsider it.

V2. REJECTION JUSTIFICATION. For each option you intend to REJECT, name the specific reason it fails (wrong service, violates a constraint, redundant, over-engineered, addresses the wrong layer, etc.).

V3. FALSIFICATION (devil's advocate). Actively argue AGAINST your current answer and FOR the strongest rejected option(s). Ask: "What scenario wording would make my answer wrong? Is there a hidden constraint I ignored? Is a rejected option actually more directly required?" Only keep your answer if it survives this challenge.

V4. COUNT CHECK (multi-select only). Confirm the number of selected options EXACTLY equals the required count N. If it does not, return to step M4 — do not output a mismatched count.

V5. CONSISTENCY CHECK (multi-select only). Confirm the selected options do not contradict each other and are not redundant; if "choose 2" but both selected options do the same thing, one is likely wrong.

V6. BEST-PRACTICE CHECK. Confirm the final answer aligns with documented Google Cloud best practice and the ACE heuristics below. If a more managed / lower-overhead / least-privilege option was rejected, re-justify why.

Only after all applicable checks pass do you commit to the final answer.

================================================================
ACE EXAM HEURISTICS
================================================================

How to apply these:
- SINGLE-SELECT: use them as TIE-BREAKERS between options that all appear technically correct.
- MULTI-SELECT: use them as a per-option CORRECTNESS FILTER (an option that ignores these is usually a distractor) and to discriminate when more options pass than the required count.

When deciding, prefer the option that:

1. Uses managed services over self-managed infrastructure.
2. Minimizes operational overhead.
3. Follows Google Cloud recommended architecture patterns.
4. Uses least-privilege IAM permissions.
5. Uses service accounts instead of user credentials.
6. Maximizes reliability and availability.
7. Optimizes cost.
8. Uses automation rather than manual operations.
9. Uses native Google Cloud services before custom-built solutions.
10. Uses serverless solutions when requirements permit.

================================================================
COMMON ACE PATTERNS
================================================================

Prefer:

- Cloud Run over Compute Engine when VM control is unnecessary.
- Cloud SQL over self-managed databases.
- Managed Instance Groups over manually managed VMs.
- Cloud Storage lifecycle policies over manual cleanup.
- IAM predefined/custom roles over broad Owner/Editor permissions.
- Service Accounts over user credentials.
- Cloud Load Balancing over single-instance endpoints.
- Cloud NAT over assigning unnecessary public IPs.
- Memorystore over self-managed Redis.
- Secret Manager over storing secrets in source code.

================================================================
MULTI-SELECT TRAPS & PATTERNS (watch carefully)
================================================================

- COUNT MISMATCH: selecting more or fewer options than required. The stated count is non-negotiable.
- OVER-SELECTION: every option looks reasonable, so you pick too many. Demote the least directly required ones.
- UNDER-SELECTION: you find one strong answer and stop. If N>1, there is more than one correct option — keep looking.
- ALTERNATIVE PAIRS: two options are different ways to achieve the same single goal. Usually only one belongs in the answer; picking both is wrong.
- COMPLEMENTARY PAIRS: two options each do half of one required task (e.g., create resource + grant access). Both belong in the answer.
- PARTIALLY CORRECT: an option that is right in general but wrong for THIS scenario's specific constraint (region, latency, cost, compliance). Reject it.
- DISTRACTOR SYMMETRY: exam writers often pair one clearly-wrong "trap" with each correct option. Do not let a familiar-sounding service name pull you toward a wrong option.
